# Development Plan

## Project

Personal Portfolio Website using PHP, HTML5, CSS3, and vanilla JavaScript.

## Working method

Development follows small, approved vertical slices. A slice includes the required presentation, PHP logic, data handling where needed, testing, and documentation updates. No implementation begins until its plan and acceptance criteria are approved.

## Phase roadmap

### Phase 1 — Project Initialization

**Status:** Complete

**Goal:** Establish the development workflow, repository baseline, AI-agent guidance, and project documentation without implementing portfolio features or deciding the visual design.

**Completed:**

- Git repository initialized.
- Initial documentation created.
- Approval-based, documentation-first workflow established.

### Phase 2 — Personal Information Gathering

**Status:** Research complete — owner confirmations recorded; content approval pending in Phase 3

**Goal:** Gather only user-provided or explicitly authorized portfolio information, then document verified content requirements.

**Findings:**

- Public GitHub profile and the four requested repositories were analyzed and documented in `PERSONAL_INFORMATION.md`.
- GitHub evidence supports project work in backend APIs, database-driven systems, vanilla JavaScript web applications, and network simulation.
- The supplied LinkedIn URL was not publicly accessible during research; no LinkedIn-specific facts were inferred from similarly named profiles.
- Education, headline, location, career direction, profile-image permission, contact details, and RW PC Trading source-only presentation have been confirmed by the owner. Additional credentials may be added if supplied; screenshot selection is deferred to a later phase.

**Remaining tasks:** Retain `PERSONAL_INFORMATION.md` as the factual source record; approve the proposed website-ready content in `CONTENT_PLAN.md` before Phase 4 begins.

### Phase 3 — Information Architecture and Content Plan

**Status:** Complete — approved by owner on 2026-11-05

**Goal:** Transform verified personal information into approved website-ready content, section hierarchy, and project prioritization without making visual-design or implementation decisions.

**Completed draft work:**

- Created `CONTENT_PLAN.md` with proposed copy for all seven planned website sections.
- Prioritized project content and recorded source-code-only treatment for RW PC Trading.
- Planned prominent placement for the verified Google IT Support Professional Certificate.

**Outcome:** `CONTENT_PLAN.md` is the approved website-content source of truth for Phase 4 visual-direction planning. Future content changes require owner approval and documentation updates.

### Phase 4 — Visual Direction

**Status:** Complete — approved by owner on 2026-11-05

**Goal:** Research and propose an approved pixel-art visual direction, UI/UX specification, asset approach, and design system before implementation.

**Draft deliverables:**

- `DESIGN_RESEARCH.md` — researched references, licensing notes, and asset guidance.
- `DESIGN_DIRECTION.md` — three pixel-art directions with a recommended Systems Console approach.
- `UI_UX_SPECIFICATION.md` — section, navigation, responsive, interaction, and accessibility specifications.
- `DESIGN_SYSTEM.md` — proposed tokens, components, pixel rules, and layout system.
- `ASSET_CATALOG.md` — researched asset candidates; no assets downloaded or approved.

**Outcome:** The approved Phase 4 baseline is the dark-only Systems Console direction, using Pixelify Sans for display headings and Inter for body text, CSS-first visuals, optional CC0 asset fallback, no avatar/mascot, no sound effects, and no required light mode. No visual assets were downloaded or selected.

### Phase 5 — Incremental Feature Delivery

**Goal:** Build approved portfolio features as tested vertical slices using the specified stack.

### Phase 6 — Quality Assurance and Release Preparation

**Status:** Not started

**Goal:** Perform responsive, accessibility, browser, security, and content checks; document deployment requirements; prepare a release candidate.

## Definition of done for a feature

A feature is complete only when its approved acceptance criteria are met, relevant tests have passed, no identified issues remain unresolved without documentation, and project documentation reflects its delivered state.
